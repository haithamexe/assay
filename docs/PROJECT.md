# Assay: project charter

Living document. Read §2 and §3 before each phase; update §6 when a decision is made and §7 when a phase finishes.
"Assay" is a working name (an assay tests the purity of metal). Rename freely.

## 1. What it is

A local-first tool for reviewing and debugging code changes, mainly code an AI agent wrote. It reaches an agent (and a person) four ways:
a CLI, an MCP server, a static HTML report, and a dashboard. One engine (`packages/core`) behind all of them.

The one idea: **evidence over opinion.** Free deterministic checks run first and cost no model tokens. Reviewers (AI) come second, blind to each other,
one lens each. Nothing a reviewer says counts unless it carries evidence you can replay. What can't be proven is shown as a hint and can't block a merge.

The demo that fixed the idea is `demo/index.html` (sample data, the Arcade look). It is the spec for the screens.

## 2. Principles (do not trade these away)

1. **Evidence over opinion.** A finding has a tier computed from its evidence, never set by hand (see §4). Only *proven* findings can block.
2. **Free first.** Everything that can be decided by code is decided by code, with 0 tokens. The model only looks where the free checks say something changed.
3. **Show before you spend.** The cost of a run is previewed before it starts, and every run has a budget. Tool answers are short; heavy artifacts stay on disk.
4. **Blind and independent.** Reviewers don't see each other until cross-exam. Their claims go through the evidence gate.
5. **Observed vs inferred.** Every sentence about impact says which. An inferred sentence never blocks.
6. **Local-first, lean.** Plain Node, `core` has no runtime dependencies, state is files (SQLite later via `node:sqlite`). No cloud, no key.
7. **Never leak.** A secret found in a diff is reported masked, never printed. Nothing leaves the computer.
8. **Standalone.** Assay needs git and Node, nothing else installed. It produces its own proof by running the project's own tests and, when a browser is already on the machine, its own page checks. Outside tools (Semgrep, gitleaks, osv-scanner, a language's mutation tool) are optional accelerators that add evidence if they are found. None is ever required, and no feature may depend on one.

## 3. Architecture

```
packages/core   the engine (no runtime deps): git facts, hunks, free checks, evidence, the gate, cases, cache, brief, report
packages/cli    the `assay` command
packages/mcp    the MCP server (`assay-mcp`)
packages/web    the dashboard: node:http + plain JS modules, loopback + a key per run + a strict CSP (built, D24 to D28)
demo/           the agreed one-file demo (sample data). `npm run demo` rebuilds it.
```

Chassis: Node 22+, ESM, `module: NodeNext`, `node:test`, tests build fixture repos in `os.tmpdir()` and set `ASSAY_HOME`.
State lives in `~/.assay` (or `ASSAY_HOME`): `cases/`, `cache/<repo>/<commit>.json`, `memory.db` (SQLite through `node:sqlite`), `packs/` (yours), `mined/`.

**Proof is built in** (phase 5, done: the tests, the revert test, mutation, and `look`, which opens pages in a browser already on the machine through Assay's own DevTools client): Assay runs the project's own test command in throwaway git worktrees of the base and the head, so a regression is a `test-fail`; reverts a risky hunk to see whether any test notices (`revert-test`); and mutates the changed lines to see which changes the tests miss (`mutation-survivor`). Later it drives a browser already on the machine through its own small DevTools client for `measurement` and `probe`. **Providers** (Semgrep, gitleaks, osv-scanner) are optional extras behind the same `Check` interface: found on PATH, they add evidence; absent, nothing changes (D13).

## 4. The model

- **Evidence**: `{ id, kind, source, what, file?, line?, replay? }`.
  - *proof kinds* (reproducible, show real behaviour): `fact` (a literal that is wrong by itself, e.g. a committed secret), `test-fail`, `probe`, `behaviour-diff`, `measurement`, `mutation-survivor`, `revert-test`.
  - *signal kinds*: `rule` (a pattern that may be harmless), `diff` (a fact about the diff that isn't a defect: no test changed, a new dependency), `history` (the file changes often), `registry`, `scope`, `claim` (a reviewer's reading).
- **Tier** (computed, `tierOf`): **proven** if any proof evidence; **corroborated** if at least two signals from distinct sources; else **hint**.
- **Finding**: `{ id, title, lens, severity, commit, file, lines, evidence[], risk, observed[], inferred[], tier }`.
- **Gate** (`gate`): a claim must cite a file and line inside the case's diff, else it is dropped (and reported as dropped). A claim with only itself as evidence is a hint.
- **Verdict**: blocked if an open proven *high* finding exists; "can merge with fixes" if open proven or corroborated findings remain; else clear.
- **Case**: a commit range, its per-commit analyses (cached by hash, so picking again is instant), its findings after merging, and what is still present in the net diff.

## 5. Phases

| # | Phase | Delivers |
|---|---|---|
| 1 | **Engine** | git facts and hunks, free checks (secrets, risky patterns, dependency changes, untested change), evidence + tier + gate, cases + cache, risk ranking, fix brief, CLI, MCP, HTML report, tests on fixture repos and a real repo |
| 2 | **Dashboard** (done 2026-11-25) | `packages/web`: the demo's screens on real cases (timeline, case file, evidence replay, running and stopping proof and page checks, before and after with measured boxes, settings). *Memory* arrived with phase 3, *Reviewers* arrives with phase 4 |
| 3 | **Memory** (done 2026-11-25) | `node:sqlite` mistake database, standards packs as files, mining `fix:` commits, hit and false-alarm stats, expiry; the dashboard's *Memory* screen, `assay memory`, the MCP tool `memory` |
| 4 | **Reviewers** (done 2026-11-25) | lenses as sub-agent prompts served by MCP, budget and routing, the cost preview, cross-exam, the Stop hook that blocks "done" without a verdict; the dashboard's *Reviewers* screen, `assay reviewers`, the MCP tools `reviewers_plan` and `reviewer_brief`. Assay never calls a model (D36). The attack pass arrived later (D50); the scoreboard arrived with phase 6 |
| 5 | **Proof** (built in; done 2026-11-25: tests, revert, mutation, and the browser checks `look`) | the project's own tests at base and head, the revert test, a mutation pass on changed lines, with the guards in D14; then Assay's own browser checks (measure a render, probe a page); function before/after. Optional providers (Semgrep, gitleaks, osv-scanner) only add evidence |
| 6 | **Calibration** (done 2026-11-25) | plant known bugs in a throwaway copy, score each reviewer, route out the ones that don't earn their tokens: `assay calibrate`, the *Scoreboard* tab. The plain-review baseline (D51) and a replay of past fix commits as a benchmark (D52) arrived later |

## 6. Decisions

- **D1 (2026-11-25) Separate tool, not a feature of an existing dev dashboard.** Its direction is "make what exists better", it already carries many MCP tools (each costs tokens in every session), and its releases are heavy. (Superseded in part by D13: no other tool is a required provider.)
- **D2 A layered chassis** (core / cli / mcp / web, no deps in core): one engine, several front ends.
- **D3 Tier is computed, never assigned.** `tierOf(evidence)` is the only place a tier is decided.
- **D4 Static rule hits are signals, not proof.** A `dangerouslySetInnerHTML` match is `rule` evidence; it becomes proven only with a probe or test. Secrets are `fact`.
- **D5 Per-commit analysis is cached by hash.** A range is the merge of its commits' analyses, plus a check of what survives in the net diff.
- **D6 Phase 1 runs nothing from the project.** No tests, no build, no network. It only reads git. Running project code arrives with providers (phase 5), with the guards in D14.
- **D7 The demo is the spec for the screens** and stays in `demo/`; the real dashboard is built from it, not from scratch.
- **D8 A reviewer can't claim proof.** Proof-kind evidence inside a claim is stored as a reading, marked "[unverified]". Only Assay, or a provider it runs, produces proof.
- **D9 An agent can't dismiss a proven finding.** MCP `finding_resolve` refuses it; a person runs `assay resolve`. Otherwise the verdict could be talked away.
- **D10 Secrets are masked at the source.** A token pattern in a test or demo path, or a key header with no key body under it, is a `rule` (hint), not a `fact`. Every snippet line goes through `redactSecrets`, and a line that is only a long base64 run is always masked, so a key body next to some other finding can't leak. Case files, caches, reports and tool answers are tested for it.
- **D11 Calibrate on real repositories before adding rules.** The first run on five real repos found false positives (a Prisma tagged template read as string-built SQL, `new-password` read as a credential, a deleted file read as a removed guard, demo HTML flooding the list, a shell `$(…)` read as a secret, the first commit's dependencies read as new). Each is fixed and pinned by a test in `calibration.test.ts`. A new rule ships with a test from a real false positive when one exists.
- **D12 Noise is capped.** At most 3 hits of one rule per file per commit, with a "N more" note on the last. Production-code rules skip test, demo, preview and docs folders. A physical CSS side is flagged only in a file that already mirrors.

- **D13 (2026-11-25) Standalone, by decision.** No required dependency on another tool. Proof comes from Assay running the project's own tests (and later a browser already installed). Other tools are optional providers at most. The earlier plan to wire an existing dev dashboard in first is withdrawn.
- **D14 Running project code is opt-in per repository.** Only the project's own test command, found from its manifest (`package.json` scripts, pytest, go test, cargo test, …) with fixed flags, in throwaway worktrees under `~/.assay`, with a time limit, never a command from a request. The first run in a repository needs the person's yes (`assay allow-run`, stored); an MCP tool can read that setting but never set it, so an agent can't grant itself permission. Results are cached by commit and command, so a second run costs nothing.

- **D15 Untested is not broken.** A revert or mutation result is proof about the *tests*, so it becomes its own Tests-lens finding (proven, never high, never blocks). On the risky hunk it adds only a `coverage` signal, which corroborates and never proves: `dangerouslySetInnerHTML` plus "no test notices" is corroborated, not proven. Only a failing test that passed before (`test-fail`) is proven *and* blocks.
- **D16 The repository is only read.** A run happens in a clean checkout made with a temporary git index (`read-tree` then `checkout-index`), not `git worktree`, so nothing in the repository's working tree, index or `.git` changes. `node_modules` is rebuilt as real folders of links, except workspace packages, which point at the checkout's own copy so the code under test is the commit's code. Links are removed before the folder, and the folder is kept if a link can't be removed.
- **D17 A red head can't be judged.** If the tests already fail at the head, reverts and mutants are skipped and it says so: "no test failed" can't be told from "tests were already failing". A mutant that fails with no failing test (it didn't compile) is invalid and not counted. A time budget stops new runs and keeps what was done: results are cached by commit, command and change, so calling `prove` again continues.
- **D18 `NODE_TEST_CONTEXT` is removed from the environment of a run.** A `node --test` started inside another `node --test` otherwise thinks it is a child and prints the wrong format. Found by running Assay's own suite through Assay.

- **D19 The browser is driven by Assay's own client, over a pipe.** `--remote-debugging-pipe` (JSON, NUL-delimited, on two inherited pipes): no port is opened, no library is installed, nothing is downloaded. It uses Chrome, Edge, Brave or Chromium if one is installed (`assay allow-run --browser <path>` otherwise) and says how to fix it if none is. The browser's cache is turned off, because two servers can get the same port one after the other and a cached stylesheet would show the wrong commit.
- **D20 Everything a browser reports is differential.** A page is opened at the head and at the base in 8 combinations (desktop and phone, light and dark, as loaded and mirrored right to left); only what is new at the head counts. That cancels whatever was already there and makes overlap measurable without false alarms. A page that is new at the head skips the noisy kinds (overlap, accessibility basics). Measured problems are `measurement` evidence (proven) and are medium at most, so they never block; an uncaught error, a blank page and a probe hit are high and do.
- **D21 A rendered problem is anchored on the line that caused it.** A changed line that names one of the element's classes or ids, in a stylesheet first; else the nearest changed line to an unchanged one that names it; else the biggest changed UI file. (A bug that first anchored on the button's markup instead of the `.place-order` rule was fixed.)
- **D22 The probe is GET and typing only.** It puts a harmless `<assay-probe>` marker in the page's query parameters (names found from forms, links and the address) and types it into text fields without submitting. If an element with that name appears, text became markup: proof, with the exploit shape. It never submits a form, and it only talks to the loopback server Assay started. Before and after pictures are compared inside the browser (no image code in the core); mirrored desktop is kept as well as the default views, because a mirrored-layout bug looks identical as loaded.
- **D23 Pages are paths on the local server, nothing else.** Anything with a scheme, starting with `//`, or containing a backslash is refused. Without a dev server command, the checkout's own files are served by a small static server that can't read outside the checkout.

- **D24 (2026-11-25) The dashboard answers one person on one computer.** It binds `127.0.0.1`, checks the `Host` header (DNS rebinding), needs a key made per run (sent once in the address, exchanged for an `HttpOnly`, `SameSite=Strict` cookie and removed from the address), needs the page's own `Origin` and a JSON body on every `POST`, and serves a page with `default-src 'none'` and scripts and styles from `'self'` only: no inline script or style. Files are served by exact name; a picture only if the case recorded it; only cases of its own repository.
- **D25 The dashboard can show `allow-run` and can't set it.** A click in a page is no stronger than a flag an agent could pass, so the permission stays a terminal command (D14). When running is off, the run buttons show a lock and pressing one shows the exact command with a *Copy* button.
- **D26 Slow or code-running work is a job.** Replay, prove and look are queued, run one at a time, say what they are doing as they go, are polled (no connection held open) and can be stopped: the core takes an `AbortSignal`, a test run's whole process tree is killed, a page check stops before its next page, and a stopped run keeps nothing (it is not cached either). A case can't be resolved while a job is using it, because both would write the same file.
- **D27 The page can't put untrusted text on screen except through one door.** Everything from git, a page or a test run goes through the `html` template tag, which escapes; sizes and positions are numbers the page computed, set with the style object. This is why the policy can ban inline script and style, and a test proves the ban by typing an inline handler into the live page. The verdict, the order of findings and each finding's state are computed once, in the core, and sent with the case.
- **D28 A picture carries what was measured in it.** `lookCase` keeps, on each screenshot, the boxes of what was measured in that combination and was not there at the base, by the same rule as the findings; the dashboard draws them as a share of the window's size, and only the kind a finding is about.

- **D29 (2026-11-25) Memory is one SQLite file, and it fails soft.** `~/.assay/memory.db` through `node:sqlite` (Node 22.13 or newer; nothing installed), every row keyed by the repository. If `node:sqlite` is missing or the file is broken, memory is off with a reason (`assay doctor`, the screen) and nothing else changes: `saveCase` and `resolveFinding` call it inside `try`, and `memoryRuntime` is a no-op. The experimental warning is swallowed at load, because it is not news to anyone using memory.
- **D30 An entry is a mistake with something that finds it, or a question.** A **standard** entry comes from a pack file and is never copied into the database (edit the file, the behaviour changes); a **learned** entry lives in the database. What finds it is Assay's own evidence (`sources` such as `rule:eval`, `browser:contrast`, `fact:*`), a pattern, or nothing (a question for a reviewer, kept and shown but never a finding). Packs are plain JSON, checked field by field, skipped and reported when bad, never executed; a pack of yours with the same id wins over a bundled one.
- **D31 Stats are read, never counted.** `hits(repo, entry, finding, commit, at, dismissed)` has one row per finding per entry, dated by its commit, so opening a case again can't count it twice and nothing drifts. A false alarm is a dismissal; *intended* is a real hit; undoing either takes it back. `saveCase` records hits and `resolveFinding` records the dismissal.
- **D32 An entry that cries wolf switches itself off, and only a signal can.** At least 4 hits, 30% or more dismissed and no real hit for 60 days; a person turning it back on gets 60 days. Only `rule:`, `diff:` and learned patterns can expire or be switched off: a finding with any proof evidence is never dropped (a test switches the secrets entry off and checks the key still shows). Switching is applied when a commit is analysed, so the timeline and the case agree, and the digest of what is switched off and what was learned is part of each commit's cache key (empty when memory changes nothing, so existing caches stay valid; a change makes a commit be analysed again once).
- **D33 A learned pattern is a signal.** It produces `rule` evidence (`memory:<id>`) and, when fixes are behind it, `history` evidence (`history:fixes`): two independent signals, so corroborated, never proven, at most medium, never blocking. A pattern added by hand with no fixes is one signal, a hint. It runs on added lines of non-test, non-generated, non-demo files, at most three per file per entry.
- **D34 Mining reads git and suggests; a person adds.** One `git log -p -U0` of up to 600 (at most 2,000) commits, per hunk the tokens a change took away (calls, members, `new X(`, CSS declarations with generic numbers), kept when at least two fix commits removed them, fixes remove them far more often than other commits do, and the fixes did the same thing with them each time (replaced them with the same token, or took them out). The pattern is the token's own characters, escaped. A suggestion can only be added from the last reading of this project's history: the page and an agent can't send a pattern. **Calibrated on real repositories:** the first version suggested project-specific names (a state setter, a ref's `.current`) because fix commits touch them; requiring the same action each time removed them, and none of three real repositories then had a suggestion worth a detector. That is a fair answer: it finds recurring things to avoid, not logic slips.
- **D35 Bundled packs hold only what can be vouched for.** OWASP Top 10 **2025** (the ten categories as listed on owasp.org/Top10/2025, mapped to Assay's checks by Assay), WCAG 2.2 AA (the criteria the page checks measure, and five that need a keyboard), and Assay's own tests, pages, basics and starter questions. Not shipped, because their text can't be vouched for and an edition is the person's choice: the OWASP Agentic list, the CWE Top 25, a team's own checklist. Those are pack files (`assay memory import`). Memory shows no pink: it is counted and mined by code, and pink is the voice of an AI.

- **D36 (2026-11-25) Assay never calls a model.** The reviewers are sub-agents of the agent the person already uses. Assay has no key and makes no network call; it plans who is worth running, hands each one a brief, and counts what comes back. This keeps Assay standalone (D13), keeps tokens off its bill, and means the dashboard can't pretend to "run" a panel: it plans, prices, gives the person the words to hand their agent, and watches what the agent reports. Spawning the sub-agents is the agent's job; an optional runner would be a separate tool.
- **D37 Routing and the budget are plain facts, and the cost is shown first.** A reviewer is relevant when the change says so (security: a flagged pattern, a sensitive path or 40 lines of logic; correctness: 10 lines; UI: a page, style or component; tests: a test changed or logic without one; supply chain: a manifest, lockfile, CI or container file; performance: an added loop, query, request or file read; triage: a request was given), each with its reason or its reason for being left out. The estimate counts characters (about four to a token) over the shared rules, the prompt, the slice and what is already known, plus 700 to answer: rough, and labelled so. The budget is spent most-justified first (more free findings in its lens, then a fixed order), keeping room for cross-examination; one that doesn't fit says "Over budget: needs 4.8k, 1.2k left". 0 is free-only. The default is 40k, per project.
- **D38 A brief is one lens and its slice, and nothing else.** The shared rules, the lens prompt (a Markdown file: yours in ~/.assay/lenses over the one that ships), only the files that lens is about with the numbers a claim must cite, what the free checks already found for it, and the memory questions for it (pack questions now carry a lens). Secrets in the diff are masked: a brief goes into a model's context. Never another reviewer's work: that reaches a reviewer only in cross-examination, after every planned reviewer has reported, anonymously. Found by a test: the first slice leaked a planted key, and the fix is the same masking as everywhere else.
- **D39 The panel lives on the case, and is counted by what the gate did.** `Case.panel` records the plan and each reviewer's state (planned, briefed, reported), claims, kept, merged and dropped. A reviewer reports through `finding_submit` (extended with `done`, `round`, `disputes`, `tokens`), so its claims meet the same evidence gate as any claim: a changed line or it is dropped, no proof, at best corroborated, never blocking. "Done" is explicit because "found nothing" can't be told from "still working" otherwise. Opening a case again keeps its panel. The kept panel is shown whatever the project budget is now, so its progress is never hidden.
- **D40 Cross-examination is a second signal, not a vote.** When every planned reviewer has reported, each claim only one reviewer made goes to the next reviewer in the ring, never its author (at most 5 each), anonymously. A confirmation is a claim of the examiner's own at the same line, so two reviewers who each saw it make the finding corroborated; a dispute is recorded and shown, and changes no tier.
- **D41 The Stop hook uses Assay's own verdict and lets go.** `assay hook stop` opens the case itself and blocks "done" only when the verdict is Blocked (or, with `--require-panel`, a planned panel is unfinished). It only looks at a branch that has left the default branch (`--always` for the last commits), lets go after 2 tries in a row on the same state, counts each session on its own, and notes that uncommitted changes aren't reviewed. `assay hook install` prints the settings to add and never edits them.
- **D43 (2026-11-25) Windows, macOS and Linux are all supported, and the suite proves it.** Assay was written and run on Windows; the platform differences were already branches in one place each (finding a browser, killing a process tree, junctions against symlinks, opening a file, `python` against `python3`). Checked on Linux (Node 22 in a container with Chromium, run as root: the browser needs `--no-sandbox` as root and a `/tmp` shared memory in a container, both now added; and a repository key must be case-sensitive on Linux). macOS can't be run from here, so it is covered by the CI matrix (Ubuntu, macOS, Windows; Node 22 and 24), which runs on every push to main and every pull request, and by hand. Its first run (2026-11-26) found what no local run could: the repository key came from how the folder was spelled, so a link to it (macOS keeps `/var` and `/tmp` behind one) or a Windows 8.3 short name was a second repository that was never allowed to run anything and had no memory; and two calibration runs started in the same second shared their cases (a flaky test). Both are fixed and pinned by tests, and the next run passed on all six.
- **D44 (2026-11-25) Bugs are planted in a throwaway repository shaped like the project, each with a clean twin.** Not a copy of the project (that would be slow, large and a way to copy someone's code around): only the files being planted, in the folders the project already uses for each language, with ordinary file names (a name like "planted_bug.js" would tell a reviewer where to look) and the same commit message on both branches. The truth is a line Assay knows: the first line of the bug's text in the file (in the base file for a removed guard). 18 templates across JavaScript and TypeScript, Python, CSS, HTML and a manifest, whichever fit. The clean twins must raise no flag from any check, so the test that asserts it also pins Assay's own false positives.
- **D45 The scoreboard is derived, never stored, and the free checks are a row of their own.** A bug is hit when a finding sits within three lines of it in the right file, and a finding counts as about the defect when it has any evidence that is not a reviewer's, a note that no test changed, history or coverage. Free cell: proven, flagged or missed. A reviewer's cell: ✓ when its claim landed on a finding that is proven (usually by the free checks), ~ when flagged without proof, ✗ for a miss in its own lens, · elsewhere, ? when it did not run; credit for a catch outside its lens. False alarms are findings on the clean case. Tokens per catch are the agent's reported figure, else the plan's estimate, marked. The two cases hold every finding and claim, so nothing needs refreshing: the page asks and the table moves as reviewers report. Assay never calls a model, so the agent runs the reviewers, on a prompt that tells it not to read the calibration folder (an honor system).
- **D46 A reviewer is left out after two runs in a row with no catch in its lens, and can be brought back.** Only finished runs count (every planned reviewer reported on both cases), once each. A lens with no planted bug for the project can't be left out. The plan says "Left out: …" with the way back (`--include`, MCP `include`); a free-only budget says "off". The record can only switch a reviewer off, never make one more trusted and never turn a hint into proof. A model varies from run to run, so one run advises and two decide.
- **D47 Calibration reads git and runs nothing.** Throwaway repositories live under ~/.assay/calibration (the newest five kept), a run id is only its fixed shape, the dashboard opens only the project's own cases so the throwaway ones never show as the project's, and the project's working tree and HEAD are checked unchanged by a test. Left out on purpose: replaying the project's own fix commits (finding the commit that introduced each fixed bug) as a more real benchmark (built later: D52), and the demo's "one plain AI review" baseline row (built later: D51).
- **D48 (2026-11-25) MIT, held by "Assay contributors".** The simplest permissive license: anyone may use, change and sell it, with the notice kept and no warranty. The copyright line names no person (this repository carries no personal data), so it can be changed to a name or an organisation later by the holder. The packages stay `private: true` (not published to npm) with `"license": "MIT"`; the bundled fonts keep their own SIL Open Font License files. Private vulnerability reporting is on, so a problem is reported on the Security tab, not in a public issue.
- **D49 (2026-11-26) The commit that broke the tests is found by running them.** When tests that passed at the base fail at the head and the range has more than one commit, Assay runs the project's tests in the middle of the range and keeps halving what is left until two neighbours remain: at most log2 of the commits (5 commits take 2 runs, 200 take 8), each run cached by commit and command, so asking again is free and a stopped search carries on. It walks the first-parent line from the base (a merge is one step) and only when that line starts at the base. It needs a green base: with a red base "passed before" means nothing for the commits in between, so it says so and searches nothing. A commit in the middle that can't be judged (the tests timed out, or could not start) ends the search with what is known ("one of N commits after X"). The finding keeps its id and its place in the range's diff, so "fixed by a later commit" still works; the culprit is `proof:bisect` evidence (`test-fail`, replayable: the two commits are run again), the title says "starting at <hash>", and when the failure's own stack points nowhere the anchor prefers the files that commit changed. A line that goes good, bad, good, bad again has more than one place where it changes; the search finds one, and what it says there is true because both neighbours were run. Off with `--no-bisect` (MCP `bisect: false`).
- **D50 (2026-11-26) The attack pass is a reviewer outside the lenses, for big budgets, and as blind as the rest.** One more brief (`attack.md`, replaceable like a lens prompt): every changed file that runs or is shown, the tests that changed by name, and what the free checks found, never another reviewer's claims; it asks for breaks (a concrete input or sequence, what the code does, what should happen) tied to a changed line. It is not a lens, because a break belongs to whichever lens it is in: each claim names that lens, so no finding is "about attack". It is planned from 80k tokens (it costs the most, and the demo put it at the biggest budget) only when a reviewer is worth running and something that runs or is shown changed, and only if it fits after the specialists and the cross-examination; below 80k it is not listed. It reports in the first round with the specialists (`reviewer_brief` lens `attack`, `finding_submit` reviewer `Attack`), cross-examination waits for it and then examines what only it claimed, and it meets the same gate: a second source at a flagged line corroborates, elsewhere it is a hint, never proof and never blocking. Not calibrated: the scoreboard scores lenses.
- **D51 (2026-11-26) The plain review is a calibration-only baseline: one reviewer, no lens, no free findings.** The demo had a row for "one plain AI review"; it is the number that says whether the panel earns its tokens. In a calibration run (never in a real review) both cases also plan a plain review (`reviewer_brief` lens `plain`, `finding_submit` reviewer `Plain`): the whole change, tests included, a generic prompt (`plain.md`, replaceable), and nothing the free checks or the memory know. It has a row and a matrix column; every bug is a chance for it; its false alarms are its flags on the clean twin; its advice compares it with the panel. It is blind like the rest, cross-examination waits for it but leaves what only it claimed alone, and it never counts toward leaving a reviewer out.
- **D52 (2026-11-26) Real bugs from the project's own history are a second benchmark, found by blame.** A fix commit (`fix:`, `bugfix:`, `hotfix:` or a subject that says it fixes something; one parent, not bulk) removes lines; `git blame` on its parent says which commit last wrote each, and where, and that line, in that commit, is the truth, but only if that commit added it and is itself an ordinary commit. Each such commit becomes a case of its own (`c-<commit>-<parent>`: real cases of the project, unlike the throwaway ones), with the panel, the attack pass and the plain review planned at 100k tokens; the free checks are scored on it at once, and reviewers by whether they flagged the line (a real bug has no known lens). Reads git and runs nothing (the working tree and HEAD are checked unchanged). It says what it is: a removed line is a proxy for the defect, only commits that call themselves fixes are used, and since nobody knows the rest of a commit is clean there are no false alarms to count, only "elsewhere" flags for information. The agent is told not to look past a case's head, because the fix is there (an honor system). The dashboard shows the scoreboard and cannot start a replay (it opens cases); it is a command. It does not feed routing: leaving a reviewer out still comes only from the planted runs.
- **D42 Only four things were left out, on purpose.** The attack pass (a reviewer that tries to break the change, in the demo at the biggest budget), which is now built (D50); the scoreboard (planting known bugs to score each reviewer), which was left for phase 6 and is now built (D44 to D47); a runner that starts the sub-agents (D36); measuring real token use (the agent may report it; otherwise an estimate).
